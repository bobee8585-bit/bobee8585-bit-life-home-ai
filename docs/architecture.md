# LIFE HOME AI 초기 아키텍처

## 원칙

1. Flutter 앱과 Next.js 웹은 NestJS REST API를 공유한다.
2. PostgreSQL을 업무 데이터의 원본으로 사용한다.
3. 모든 메뉴는 `ACTIVE`, `HIDDEN`, `READ_ONLY`, `INTAKE_DISABLED`,
   `DISABLED`, `MAINTENANCE` 상태를 서버에서 판정한다.
4. 부동산 서비스는 초기 `ACTIVE`, 확장 서비스는 초기 `HIDDEN`으로 둔다.
5. 인증, 권한, 메뉴 상태, 입력 검증을 통과한 요청만 업무 로직을 실행한다.

## 접근 제어 순서

1. JWT와 활성 세션을 검증한다.
2. 필요한 역할을 검증한다.
3. 데이터베이스에서 현재 유효한 세부 Permission을 검증한다.
4. 메뉴 정책을 역할·플랫폼·국가·지역·기간·우선순위로 판정한다.
5. 읽기 또는 쓰기 가능 상태일 때만 업무 로직을 실행한다.

긴급 정책이 일반 정책보다 우선하며, 그다음 조건의 구체성, 정책 우선순위
순으로 적용한다. 서비스 모듈 자체가 숨김 또는 중단 상태이면 하위 메뉴를
활성화하지 않는다.

## 등록자와 매물 상태 흐름

- 중개사 신청: `PENDING → ACTIVE` 또는 `REJECTED`
- 중개사 승인: 중개사무소 활성화, `BROKER`·`BROKER_MANAGER` 역할 부여
- 중개사 매물 작성: 승인된 중개사와 활성 중개사무소만 허용
- 직거래 매물 작성: 휴대폰 인증 회원이 소유·위임 증빙과 금지사항 확인 제출
- 매물 검수: `DRAFT → PENDING_REVIEW → ACTIVE` 또는 `REJECTED`
- 직거래 승인: 소유·위임 증빙 `PENDING → VERIFIED`와 매물 `ACTIVE`를 원자 처리
- 공개 조회: `ACTIVE` 매물과 `isPublic=true` 미디어만 반환
- 거래 진행: `AVAILABLE ↔ RESERVED/CONTRACTING → COMPLETED/WITHDRAWN`
- `COMPLETED`, `WITHDRAWN`은 매물 공개 상태를 `INACTIVE`로 원자 변경
- 모든 승인·반려·가격·거래 상태 전이는 감사 로그에 기록

직거래 매물은 `OWNER_DIRECT`, `DIRECT_OWNER`, `brokerageFee=NONE`으로
표시하고 중개사무소는 연결하지 않습니다. 증빙 참조값은 AES-256-GCM으로
암호화하며 관리자 검수 응답 외에는 원문을 반환하지 않습니다. 일반회원은
플랫폼에서 타인의 거래를 반복 알선하거나 중개수수료를 받을 수 없습니다.

## 매물 채팅 흐름

1. 회원이 활성 매물에서 채팅방 생성을 요청한다.
2. 중개사 매물은 담당 중개사, 직거래 매물은 등록 회원을 상대방으로 고정한다.
3. 동일 회원·매물 조합은 데이터베이스 고유키로 한 채팅방만 허용한다.
4. 메시지는 방별 원자 증가 순번과 `clientMessageId` 멱등성 키로 저장한다.
5. 참가자별 마지막 읽음 순번은 조건부 갱신으로 항상 증가만 한다.
6. 메시지 생성과 상대방 알림 아웃박스·감사 로그를 한 트랜잭션에 기록한다.
7. 매물이 `ACTIVE`가 아니면 기존 기록 조회는 허용하고 신규 전송은 차단한다.

현재 전송 계약은 최대 2,000자의 텍스트와 REST 기반 조회를 사용합니다.
채팅방·메시지는 두 참가자만 조회할 수 있고 비참가자에게는 존재 여부도
노출하지 않습니다. 푸시·SMS에는 매물번호와 채팅방 식별자만 전달하고 메시지
본문은 알림 payload와 감사 로그에 저장하지 않습니다. 채팅은 푸시 전용
알림으로 분류해 푸시 토큰이 없는 경우 SMS로 대체하지 않고 `SKIPPED`로
종결합니다. 실시간 소켓 전송을 추가하더라도 PostgreSQL 메시지 순번과 동일한
권한·멱등성 규칙을 원본으로 유지합니다.

## 전자계약 흐름

1. 확정 또는 완료된 방문 예약의 회원·매물 등록자만 계약을 생성한다.
2. 양쪽 휴대폰 본인인증, 필수 동의와 활성 공급자를 검증한다.
3. 예약별 고유키로 계약 중복을 막고 당사자 두 명을 고정한다.
4. 계약 상태를 원자적으로 선점한 뒤 계약 ID를 멱등성 키로 공급자 세션을 만든다.
5. 공급자 콜백의 원문 HMAC와 이벤트 ID·본문 해시를 검증한다.
6. 당사자별 상태는 `PENDING → VIEWED → SIGNED/DECLINED` 방향으로만 갱신한다.
7. 서명 완료 문서 참조값은 암호화하고 SHA-256 무결성 해시만 응답에 제공한다.
8. 서명 완료 시점을 기준으로 10년 보존 기한을 설정하고 이력·감사·알림을
   같은 트랜잭션에 기록한다.

실제 본인확인과 전자서명은 선택한 외부 공급자가 담당합니다. 개발용 모의
공급자는 운영 환경에서 차단하고 운영 게이트웨이는 HTTPS, API 키, 원문 웹훅
서명을 강제합니다. 계약 문서 참조값은 API·알림·감사 로그에 복사하지 않습니다.

## 미디어 처리 흐름

1. 매물 등록자가 초안·반려 또는 거래 진행 중인 활성 본인 매물에 파일을 업로드한다.
2. API가 파일 유형·크기와 매물별 공개/전체 개수 제한을 검증한다.
3. 원본을 비공개 객체 저장소에 기록하고 상태를 `REQUESTED`로 생성한다.
4. Redis 큐에 `uploadId`만 담은 결정적 작업을 등록하고 HTTP 202를 반환한다.
5. 별도 작업자가 원본을 임시 작업 디렉터리에 내려받아 `PROCESSING`으로 전환한다.
6. 이미지는 WebP, 동영상은 H.264/AAC MP4로 변환하고 JPEG 썸네일을 만든다.
7. 결과를 객체 저장소에 올리고 `PropertyMedia` 연결과 `READY` 전환을 한
   데이터베이스 트랜잭션으로 처리한다.
8. 성공하면 원본과 임시 파일을 폐기한다. 일시적 실패는 지수형 지연으로
   재시도하고, 영구 오류 또는 최대 시도 초과는 `FAILED`로 종료한다.

공개 파일은 활성 매물의 공개 미디어에만 허용합니다. 비공개 미리보기는
매물 등록자 또는 매물 승인 권한자에게만 허용합니다. 객체 키는 직접 공개하지
않고 API가 권한을 확인한 뒤 스트리밍합니다. 운영 환경은 S3 호환 비공개 버킷과
서버 측 AES-256 암호화를 강제하며 로컬 어댑터는 개발 환경에서만 허용합니다.
작업자 수와 동시성은 독립 확장할 수 있고 Redis 작업 ID는 `uploadId`로 고정해
같은 요청의 중복 등록을 막습니다.

미디어 개수 제한은 완료된 `PropertyMedia`뿐 아니라 `REQUESTED`와 `PROCESSING`
업로드를 함께 계산합니다. 원본 저장 뒤 매물 행을 잠그고 제한을 다시 확인하여
동시에 들어온 요청이 이미지·동영상 전체 및 공개 개수를 초과하지 않게 합니다.

## 허위 매물 신고 흐름

- 신고 상태: `OPEN → UNDER_REVIEW → RESOLVED` 또는 `REJECTED`
- 같은 회원이 동일 매물에 미처리 신고를 중복 제출할 수 없음
- 매물 소유 중개사는 본인 매물을 신고할 수 없음
- 종료 상태의 신고는 다시 열 수 없음
- 처리 완료 시 관리자 선택으로 매물을 `INACTIVE`로 전환
- 생성과 모든 검수 전이를 전용 이력 및 감사 로그에 기록

## 환율과 표시 가격 흐름

1. 앱은 지원 통화 목록을 확인하고 `displayCurrency`를 선택한다.
2. 매물 API는 원금 통화를 변경하지 않고 원금·보증금·월세를 함께 변환한다.
3. 통화쌍 캐시가 15분 이내이면 저장된 환율을 사용한다.
4. 캐시가 만료되면 외부 공급자에서 최신 환율을 받아 갱신한다.
5. 공급자 장애 시 7일 이내 마지막 정상값을 `isStale=true`로 반환한다.
6. 응답에는 공급자, 기준 시각, 적용 환율과 `DISPLAY_ONLY` 용도를 포함한다.

환율은 `exchange_rates`에 통화쌍별로 저장됩니다. 기본 공급자는 중앙은행
기준 환율을 수집하는 Frankfurter이며, 결제·정산이 아닌 매물 가격 표시용입니다.
상용 실시간 환율이 필요한 경우 공급자 어댑터를 교체하고 동일한 캐시·장애
대체 정책을 유지합니다.

## 방문 예약 상태와 알림 흐름

1. 휴대폰 인증 회원이 활성 매물에 방문 희망 시간을 요청한다.
2. 요청은 `REQUESTED`로 저장되며 자동 확정하지 않는다.
3. 매물 등록자만 승인·거절·대안 시간 제안을 할 수 있다.
4. 승인은 요청 시간을 `CONFIRMED`로 확정한다.
5. 대안 제안은 `ALTERNATIVE_PROPOSED`가 되며 회원이 직접 수락해야 확정된다.
6. 회원은 요청·대안 대기·확정 상태에서 시작 전 취소할 수 있다.
7. 모든 전환은 이력과 감사 로그에 기록하고 상대방 알림을 같은 트랜잭션의
   `notification_outbox`에 적재한다.

요청 시간은 최소 2시간 전, 30분~3시간, 90일 이내로 제한합니다. 회원과
매물 등록자의 겹치는 예약을 확인하며, 동일 회원·매물의 처리 중 또는 확정
예약은 부분 고유 인덱스로 한 번 더 차단합니다. 알림 아웃박스는 전달 보장을
위한 저장 계층입니다.

알림 작업자는 만료 가능한 잠금으로 배치를 선점하고 FCM 푸시를 우선
전송합니다. 활성 토큰이 없거나 공급자가 토큰을 영구 무효로 판정하면 인증된
국내 휴대폰으로 SENS SMS를 대체 전송합니다. 공급자 일시 장애에는 SMS를
중복 전송하지 않고 지수형 지연으로 재시도합니다. 최대 횟수를 초과하거나
전송 대상이 없으면 `FAILED`로 종료합니다.

푸시 토큰은 AES-256-GCM으로 암호화하고 검색·중복 판정에는 키 기반 해시만
사용합니다. 앱에는 토큰 자체를 다시 반환하지 않으며, 로그와 오류 필드에는
전화번호·토큰·알림 본문을 기록하지 않습니다. FCM은 서비스 계정에서 만든
단기 OAuth 2.0 토큰을 사용하고, SENS는 요청 시각·메서드·URI·Access Key의
HMAC-SHA256 서명을 사용합니다.

## 여러 매물 방문 동선 계획

1. 휴대폰 본인인증 회원이 공개 매물 2~5개와 출발 좌표·시각을 제출한다.
2. 비공개 매물, 본인 매물, 좌표가 없는 매물은 계산 전에 차단한다.
3. 최대 120개 전체 순열을 비교하여 출발지부터 모든 매물을 방문하는 최단
   순서를 결정한다.
4. 자동차·대중교통·도보 프로필별 도로 보정거리와 평균속도로 이동시간을
   추정한다.
5. 매물별 방문시간과 완충시간을 더해 제안 방문 구간·전체 완료시각·완료
   희망 시각 충족 여부를 반환한다.
6. 제안 일정은 예약을 자동 생성하거나 확정하지 않으며, 각 방문은 기존
   예약 요청과 해당 매물 등록자 승인 절차를 거친다.

현재 계산은 Haversine 직선거리와 보수적인 도로 보정계수 기반의 예약 전
계획치입니다. 응답에 실시간 교통 미포함을 명시하며, 운영용 지도 공급자를
연결할 때도 같은 응답 계약과 매물 등록자 승인 정책을 유지합니다.

## 예약금 결제와 환불 흐름

1. `CONFIRMED`이고 시작 전인 본인 예약만 예약금 결제를 준비한다.
2. 서버가 금액·통화·환불 정책 버전을 결정하고 회원 동의를 스냅샷으로 저장한다.
3. 결제 준비와 승인은 서로 다른 멱등성 키와 거래 원장을 사용한다.
4. 공급자 승인이 완료되면 예약금은 `PAID`, 방문 권한은 true가 된다.
5. 방문 전 회원 취소는 예약 상태 변경과 함께 100% 환불 요청을 원자적으로 생성한다.
6. 환불 성공 시 `REFUNDED`, 공급자 실패 시 `REFUND_PENDING`을
   유지하여 동일 공급자 멱등성 키로 재처리한다.
7. 환불 요청부터 3일의 보수적인 내부 처리기한과 연체 여부를 추적한다.

결제 카드번호·CVC는 저장하지 않고 PG 공급자 참조값만 보존합니다. 개발용
공급자는 `NODE_ENV=production`에서 사용할 수 없습니다. 카드 가맹점 수수료는
회원에게 전가하지 않으며, 현재 국내 정책에서는 환경설정으로도 방문 전 환불률을
100% 미만으로 낮출 수 없습니다. 0.8.0의 미처리 70% 환불은 전액으로 수정하고,
이미 부분 환불된 결제는 잔여액을 별도 멱등성 키의 추가 환불로 생성합니다.
향후 서비스 제공 개시 후 공제 정책이 필요하면 별도 법률 검토와 약관 버전을
거쳐 새로운 정책으로 구현해야 합니다.

## 운영 PG와 웹훅 검증

운영 기본 PG는 `PAYMENT_PROVIDER_MODE`로 선택하지만, 이미 생성된 결제의 환불과
수신 웹훅은 저장된 공급자 기준으로 처리합니다.

| 공급자 | 서버 인증 | 승인·취소 검증 | 공개 설정 |
|---|---|---|---|
| Toss | 서버 시크릿 Basic 인증 | 승인·취소 멱등성 키, 거래 재조회 | 클라이언트 키 |
| NICEPAY | `clientKey:secretKey` Basic 인증 | 응답 `tid + amount + ediDate + secretKey` SHA-256 서명 | 클라이언트 키 |
| NHN KCP | 서비스 인증서 | 개인키 RSA-SHA256 서명, 거래 재조회 | 사이트 코드 |

KCP 인증서와 개인키는 줄바꿈 손상을 막기 위해 Base64 환경변수로 주입하며,
개인키 암호가 있으면 별도 환경변수로 전달합니다. 인증서·개인키·PG 시크릿은
소스, 데이터베이스, 앱 설정 응답에 저장하지 않습니다.

웹훅은 다음 순서로 검증합니다.

1. 토스 공식 전송 ID 또는 나이스·KCP 본문의 공급자 식별값 해시를 공급자별
   유일키로 저장한다.
2. 같은 전송 ID와 본문 해시는 한 번만 처리하고, 본문이 달라지면 거부한다.
3. PG별 서버 자격증명으로 결제를 공급자 API에서 다시 조회한다.
4. 조회된 주문번호·금액·통화가 예약금 원장과 모두 일치할 때만 반영한다.
5. 승인 응답이 유실됐으면 `PAID`로 복구하고, 외부 취소가 완료됐으면
   누적 취소액을 기준으로 `PARTIALLY_REFUNDED` 또는 `REFUNDED`로 재조정한다.
6. 모든 수신·실패·처리 결과는 `payment_webhook_events`와 감사 로그에 남긴다.

웹훅 주소는 `/v1/payment-webhooks/toss`, `/nicepay`, `/nhn-kcp`입니다. KCP
`TX00`은 가상계좌 거래를 `PAVC` 유형으로 재조회하며 성공 응답은 엔벌로프 없이
`{"result":"0000"}`을 반환합니다. 카드번호·CVC·서버 비밀정보와 웹훅 원문은
저장하지 않으며, 원문 대신 SHA-256 해시만 보존합니다.
